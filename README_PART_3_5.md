# Блок 3, подчасть 3.5 — маршрутизация сообщений, геометки, запуск

Последняя подчасть Блока 3 («Telegram-бот на единый API»). После неё
Блок 3 закрыт целиком.

Патч, не полный проект — распаковать поверх существующего `backend/`
(после уже применённых патчей частей 3.1-3.4), файлы лягут по тем же
путям:

```
backend/legacy/telegram_bot.py    — заменить целиком (маршрутизация
                                     сообщений/гео-заметки переведены на
                                     HTTP; run_bot()/migrate_schema —
                                     рассмотрены и сознательно оставлены)
backend/app/routers/bot.py        — заменить целиком (добавлен
                                     POST /api/bot/geo-notes)
PLAN_DORABOTKI-2-4.md             — обновлённый план (3.5 отмечена ✅,
                                     Блок 3 закрыт целиком)
```

`backend/legacy/db.py` не менялся — гео-заметки не потребовали новой
функции там (см. ниже, почему). `backend/app/main.py`,
`backend/legacy/config.py`, `backend/requirements.txt` тоже не менялись.
Переменные окружения — те же, что и в частях 3.1-3.4
(`LESOVOD_API_BASE_URL`, `LESOVOD_BOT_SERVICE_TOKEN`,
`LESOVOD_TELEGRAM_BOT_TOKEN`), новых не добавилось.

## Что именно сделано

1. **Гео-заметки** (кнопка «📍 Добавить заметку на делянку»). Новая
   HTTP-обёртка `save_geo_note(telegram_id, coords, note_text,
   photo_path)` в `telegram_bot.py` → `POST /api/bot/geo-notes` (новый
   эндпоинт в `app/routers/bot.py`, за тем же `require_permission
   ("bot.access")`, что и весь остальной роутер). Раньше это делала
   `_save_geo_note(cursor, ...)`, определённая прямо в `telegram_bot.py`,
   писала в таблицу `geo_notes` по общему sqlite-соединению бота, без
   своего `commit()` — коммитил вызывающий код (`handle_message`/
   `handle_photo`). Функция удалена как дублирующая (тот же принцип, что
   в 3.1/3.2 с `_save_registration`/`save_raw_report`).

   **Отличие от подчастей 3.2-3.4**: INSERT сделан прямо в роутере, а не
   как новая функция в `legacy/db.py`. Таблица `geo_notes` — простой
   append-лог без update/upsert-логики (в отличие, например, от
   `lesorub_directory`, где `upsert_worker()` из части 3.1 тоже, к слову,
   делает SQL прямо в роутере — тот же паттерн, не новый для этого
   файла). Заводить отдельную функцию в `db.py` ради одного `INSERT`
   показалось лишним слоем косвенности.

2. **`handle_message`** — четыре места, где раньше открывался `get_db()`
   ради `cursor` (только для того, чтобы передать его в
   `_require_registered_user`, которая с части 3.1 этот параметр не
   использует), переведены на `_require_registered_user(telegram_id)`
   без параметра. Пятое место — привязка текстового комментария к
   ожидающей гео-метке — переведено на `save_geo_note()`.

3. **`handle_photo`** — фото-комментарий к геометке тоже переведён на
   `save_geo_note()`; `download_photo()` не менялась (как и раньше —
   вызовы Telegram Bot API + запись на диск бота, не наш backend).

4. **`handle_location`** — рассмотрена, **оставлена без изменений**: она
   и раньше не обращалась к БД вообще, только кладёт координаты в
   `_pending_geo` (память процесса, не таблица) — переводить было нечего.
   Добавлено пояснение в докстринг, чтобы это не читалось как забытый
   хвост.

5. **`run_bot()` / вызов `migrate_schema` при старте** — рассмотрены и
   **сознательно оставлены без изменений**. Подробное обоснование — в
   докстринге самой функции; коротко: backend и так вызывает
   `migrate_schema` сам на своём старте, но `handle_balance_callback`
   (сознательное исключение части 3.4) по-прежнему держит своё прямое
   sqlite-соединение к тому же `DB_PATH` — бот не может полагаться на
   гарантированный порядок «backend стартовал первым» без явной
   настройки зависимостей служб (Блок 4, Windows). `migrate_schema`
   идемпотентна и вызывается один раз на старт процесса, а не на каждое
   сообщение — цена пренебрежимо мала. Если/когда `handle_balance_callback`
   тоже переедет на HTTP (вариант «а» из решения части 3.4, сознательно
   не выбранный там) — тогда у бота не останется ни одного прямого
   обращения к БД, и этот вызов вместе с `DB_PATH`/`get_db()`/
   `import sqlite3` можно будет убрать одним заходом; это отдельная,
   не входящая в объём 3.5 правка.

6. **`_require_registered_user(cursor, telegram_id)` → `_require_registered_user(telegram_id)`.**
   Параметр `cursor` убран из сигнатуры — он не использовался функцией
   уже с части 3.1 (проверка регистрации ходит по HTTP через
   `get_worker()`), подчасти 3.2-3.4 уже передавали `None` вместо него,
   а часть 3.5 перевела последние 4 места в `handle_message`, ещё
   передававшие реальный `cursor`. Все 15 вызывающих мест в файле
   обновлены одним заходом на новую однопараметрическую сигнатуру —
   если где-то в других патчах найдётся двухаргументный вызов, это
   забытое место, не альтернативная сигнатура.

## Итог по всему Блоку 3 после этой подчасти

Единственное оставшееся прямое обращение бота к БД —
`get_remaining_volumes_for_bot` в `handle_balance_callback`
(сознательное исключение части 3.4, находка №1 аудита — ЕГАИС-сверка,
подробности в комментарии у её импорта в начале `telegram_bot.py`) — и
сама возможность его сделать (`get_db()`/`DB_PATH`/`import sqlite3`,
нужны также для `migrate_schema` в `run_bot()`, решение п.5 выше). Всё
остальное — 14 исходных точек прямого импорта из `db.py`/`raskhod.py` и
~33 места прямой работы со sqlite внутри хендлеров (находка аудита,
часть 1 плана) — переведено на HTTP через `app/routers/bot.py`, плюс
один прямой своп таксационной карточки на уже существующий
`app/routers/taxation.py` (часть 3.4, находка «низкий риск»).

## Проверено

- `ast.parse` проходит на обоих изменённых файлах (`telegram_bot.py`,
  `app/routers/bot.py`).
- Прямой импорт `telegram_bot.py` — падений на отсутствующих символах
  нет. `_save_geo_note` в модуле больше не определена (удалена
  осознанно, не забыта); `save_geo_note`, `get_db`, `run_bot`,
  `handle_location` — на месте, как и решено выше;
  `_require_registered_user` — новая однопараметрическая сигнатура.
  (Для самой проверки импорта в этой среде понадобились временные
  заглушки `config.get_api_base_url()`/`config.DOLZHNOSTI*` — они уже
  есть в вашем реальном `config.py` с части 3.1, просто не входили в
  присланные архивы этого захода; в патч они не включены и не нужны.)
- **Сквозной прогон через реально поднятый `uvicorn`** (не только
  `TestClient`, как и в части 3.4) — `save_registration()`, затем
  `save_geo_note()`, вызваны по-настоящему, по сети, против настоящего
  сервера: запись реально появилась в таблице `geo_notes` (проверено
  прямым SQL-запросом к файлу базы) с верными `telegram_id`/`lat`/`lon`/
  `note_text`; запрос на `POST /api/bot/geo-notes` без токена → 401, как
  и на всех остальных эндпоинтах `app/routers/bot.py`.
- Полноценный прогон живого бота против настоящего Telegram (реальные
  `handle_location`/`handle_message`/`handle_photo` через
  `bot.infinity_polling()`) не делался — в среде, где готовился патч,
  нет доступа к Telegram Bot API; проверены только сами HTTP-обёртки и
  их использование внутри хендлеров (по коду и через прямой вызов
  функций, см. выше), сам `telebot`-роутинг не менялся.
