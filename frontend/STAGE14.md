# Этап 14. Абрис — последний экран плана

## Ключевая находка

Абрис в desktop-версии — это НЕ Qt-виджет с нуля, а уже готовый
самодостаточный HTML/JS-инструмент (`abris_tool.html`, ~3000 строк:
чертёжная доска на `<canvas>`/SVG, слои, история undo/redo, экспорт в
PDF через html2canvas+jsPDF, булевы операции через clipper.min.js),
встроенный в приложение через `QWebEngineView`. Единственное, что было
специфично для Qt — маленький мост `QWebChannel`/`pyBridge` на 20 строк
в самом конце файла, который принимал готовый PNG (`canvas.toDataURL()`)
и сохранял его на диск + в БД (`delyanka.save_abris_image`).

Поэтому перенос — не переписывание с нуля, а точечная замена этого моста:
сам редактор (все ~3000 строк логики рисования/экспорта) перенесён
**без изменений**.

## Что сделано

```
frontend/public/
├── abris_tool.html          # тот же файл, с одной правкой (см. ниже)
└── vendor/abris/
    ├── html2canvas.min.js   # те же библиотеки, что грузил desktop
    ├── jspdf.umd.min.js     # локально (не с CDN) — то же оффлайн-
    └── clipper.min.js       # соображение, что было в исходном комментарии
```

Правка в `abris_tool.html` — один блок в самом конце (искать
"Сохранение в веб-приложение"):
- Убран `<script src="qrc:///qtwebchannel/qwebchannel.js">` и весь код
  `QWebChannel`/`window.pyBridge`.
- `item_id` берётся из query-параметра страницы (раньше передавался в
  Python-конструктор `AbrisDialog`, теперь — `?item_id=...` в URL).
- Сохранение — обычный `fetch(... , {method: "POST", body: FormData})`
  на `POST /api/delyanki/items/{item_id}/abris` (тот же эндпоинт, что уже
  был готов в `delyanki.py` с Этапа 5 — `upload_abris`), вместо
  `pyBridge.receive_image(dataURL)`.
- Если страница открыта из другой вкладки (`window.opener` есть) —
  после успешного сохранения шлёт `BroadcastChannel("lesovod-abris")`,
  чтобы открывшая вкладка (экран "Делянки") могла обновить список без
  ручного F5.
- Пути к трём библиотекам — с `html2canvas.min.js` на
  `/vendor/abris/html2canvas.min.js` (и так же для двух других).

Остальные ~2980 строк (вся логика рисования, слоёв, PDF-экспорта,
пресетов экспорта) — **не тронуты**.

## Frontend (Plots.jsx)

- В таблице выделов делянки — колонка "Абрис" с кнопкой:
  "🧭 Нарисовать" (если `abris_image_path` пуст) / "✅ Открыть/перерисовать"
  (если абрис уже есть) — открывает `abris_tool.html` в новой вкладке
  (`window.open`, не встроенный компонент: инструмент самодостаточен,
  со своим топбаром/навигацией, и не рассчитан на то, чтобы жить внутри
  React-дерева — та же логика, по которой desktop открывал его отдельным
  диалогом, а не встраивал в основной экран).
- Карточка делянки подписана на `BroadcastChannel("lesovod-abris")` —
  после сохранения абриса в другой вкладке список выделов обновляется
  автоматически.

## Проверено руками (не только синтаксис)

- `node --check` на обоих inline `<script>` блоках файла — OK.
- `vite build` + `vite preview` — `abris_tool.html` и все три
  библиотеки отдаются с кодом 200, код нового блока сохранения
  присутствует в собранном файле.
- `POST /api/delyanki/items/{id}/abris` — сквозной тест через
  `TestClient` с фейковым PNG, запись реально попадает в
  `storage/uploads/`.

## Не перенесено (осталось как в desktop)

Сам эндпоинт `upload_abris` (не менялся, Этап 5) не проверяет, что
`item_id` существует, — `UPDATE` по несуществующему id просто ничего не
меняет, без ошибки. Это поведение унаследовано из
`delyanka.save_abris_image` как есть, не считается багом этого этапа.

## Итог

Все экраны из Sidebar перенесены. Из всего исходного desktop-приложения
сознательно не перенесены только кросс-экранные фрагменты, которых нет
в плане веб-версии вообще (см. STAGE13.md: "Рубки ухода", "Осветление")
— в остальном план закрыт полностью.
